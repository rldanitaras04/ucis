# Stage 2 — Corrected UCIS Architecture Specification

## 2.1 Authoritative security model

Use **permission + scope + role-specialization** as the authorization model.

- Roles identify organizational/clinical capabilities.
- Permissions identify allowed actions.
- Scope identifies the organizational or clinical boundary.
- Provider specialization identifies medical vs dental authority.
- Clinical PHI access requires a valid clinical role, required permission, active provider profile, valid provider assignment, matching clinic/service/effective dates, and encounter relationship.
- ADMIN and SUPER_ADMIN never contribute clinical scope by themselves.
- A user with ADMIN + DOCTOR accesses clinical records only through the DOCTOR permission/clinical path.

## 2.2 Clinical authorization chain

Every provider clinical authorization must resolve:

`auth.uid → active user_profile → active provider_profile → provider_type → required permission → active provider_assignment → clinic → clinic_service → effective dates → encounter → target clinical record`

For a provider accessing a record, the record's encounter must be assigned to that provider unless the explicitly defined care-team rule grants access.

## 2.3 Clinical scope decisions

- DOCTOR: assigned medical encounters only.
- DENTIST: assigned dental encounters only.
- NURSE: assigned care-team/encounter scope only; no clinic-wide clinical-record access.
- CLINIC_STAFF: operational/queue/document support access only; no unrestricted clinical notes.
- ADMIN: administrative data only unless independently holding a clinical role.
- SUPER_ADMIN: system administration only unless independently holding a clinical role.
- STUDENT/FACULTY/NON_TEACHING_STAFF: own permitted patient-facing records only.

## 2.4 Specialty separation

Explicit database policies must enforce:

- Doctor cannot SELECT/INSERT/UPDATE dental clinical records through the medical role.
- Dentist cannot SELECT/INSERT/UPDATE medical clinical records through the dental role.
- Specialty separation applies to SELECT as well as writes.

## 2.5 Patient identity

`patient_profiles.user_profile_id` is unique for the one-to-zero-or-one relationship.

`user_profiles` is authoritative for authenticated identity/account status. `patient_profiles` is authoritative for patient-specific clinical identity/type. Duplicated campus/university fields must either be derived or constrained to match the authoritative organization relationship.

## 2.6 Queue

Queue numbers must be generated by a controlled transaction using `queue_counters` keyed by clinic/service/date. Generation must lock or atomically update the counter and enforce a unique constraint on `(clinic_id, service_id, queue_date, queue_number)`.

## 2.7 Encounter invariants

Encounter, queue, clinic, service, patient and provider relationships must be mutually consistent. Circular FKs must be created in phases or made deferrable where appropriate.

## 2.8 Finalized records

Finalized medical and dental records are immutable as a whole. No UPDATE may change any field, including status, after finalization.

Corrections use amendment records containing:

- original record reference
- amendment reason
- requested/corrected data
- actor
- timestamp
- authorization evidence
- approval/finalization status

An amendment never silently rewrites the historical finalized record.

## 2.9 Pharmacy

Dispensing is a single atomic transaction:

1. authorize caller;
2. validate prescription item;
3. lock eligible batch row(s);
4. verify expiry and available quantity;
5. deduct stock;
6. create dispensing record;
7. create inventory movement;
8. commit.

Concurrent final-unit dispensing must yield exactly one success.

## 2.10 FBS

FBS records are confidential clinical data. They are never available through administrative scope alone. Any AI or rule-based flag is informational and must not be represented as an autonomous diagnosis.

## 2.11 Documents and QR verification

Official certificates/clearances may expose a verification token/QR code. Anonymous verification is RPC-only and returns only minimal authenticity metadata. No patient ID, name, diagnosis, notes, or clinical payload is returned.

Verification codes must be cryptographically strong and rate-limited at the application/edge layer.

## 2.12 Audit

Audit logs are append-only. Application roles cannot UPDATE/DELETE/TRUNCATE them.

Because ordinary PostgreSQL triggers do not audit SELECT operations, sensitive read auditing must be implemented through controlled data-access functions/application instrumentation for designated PHI tables. The architecture must explicitly identify which read events are audited.

Audit data must minimize PHI and record actor, action, object type/id, timestamp, outcome, request/correlation ID, and changed-field metadata where appropriate.

## 2.13 SECURITY DEFINER

Every SECURITY DEFINER function requires:

- exact signature;
- owner;
- fixed `search_path`;
- explicit caller class;
- explicit EXECUTE grants;
- authorization predicates;
- parameter validation;
- RLS bypass rationale;
- data-access scope;
- abuse/DoS considerations;
- negative tests.

Privileged functions must not be executable by PUBLIC unless explicitly designed as a narrow public verification function.

## 2.14 Status transitions

Every status-bearing workflow has an explicit transition graph. Invalid transitions raise errors. Finalized states cannot revert to draft.

## 2.15 Deletion

Clinical and audit data are not physically deleted by application roles. Lifecycle states such as archived/cancelled/revoked/inactive are used. Any exceptional administrative purge must be separately authorized, controlled, audited, and outside ordinary application permissions.

## 2.16 Break-glass

Emergency access, if retained, must require reason, actor, target patient/record, start/end time, approval policy, elevated audit logging, and automatic expiration. Break-glass never becomes permanent scope.

## 2.17 Storage

Clinical documents reside in private storage. No public bucket is used for PHI. Downloads use short-lived authorized signed URLs generated only after record-level authorization.

## 2.18 Realtime

Realtime subscriptions are disabled for sensitive tables unless the channel authorization itself is proven equivalent to RLS. Queue/status updates should use narrowly scoped channels or server-mediated events.

## 2.19 AI

AI is advisory only:

- no autonomous diagnosis;
- no autonomous prescription;
- no autonomous clearance decision;
- no arbitrary SQL;
- no service-role key exposure;
- inputs must be authorization-filtered;
- outputs are drafts until authorized provider approval;
- AI interactions are auditable.

# Stage 4 — Second Re-Audit Gate

Before production SQL, perform a fresh adversarial audit against the corrected architecture, not against the previous report.

## Mandatory pass criteria

### Authorization

- ADMIN alone cannot access clinical PHI.
- SUPER_ADMIN alone cannot access clinical PHI.
- ADMIN + DOCTOR accesses only the DOCTOR clinical path.
- ADMIN + DENTIST accesses only the DENTIST clinical path.
- ADMIN + NURSE accesses only the NURSE clinical path.
- Administrative scope never grants clinical scope.
- Doctor cannot access dental records.
- Dentist cannot access medical records.
- Nurse cannot access unrelated encounters.

### Patient isolation

A user knowing another patient's UUID receives zero rows through direct table access and controlled APIs.

### Clinical integrity

- Finalized medical records cannot be modified.
- Finalized dental records cannot be modified.
- Amendments create auditable correction records.
- Invalid status transitions fail.
- Physical DELETE fails for protected clinical/audit records.

### Concurrency

- 100 concurrent queue requests produce unique queue numbers.
- Two concurrent final-unit dispense attempts produce exactly one success.
- Inventory never becomes negative.

### Public verification

- anon has no direct table access to clinical/document verification data.
- QR RPC returns only allowlisted fields.
- invalid/expired/revoked tokens fail appropriately.
- rate limiting is defined outside the database where appropriate.

### SECURITY DEFINER

No privileged function may be directly invoked by an unauthorized caller or used to bypass the intended authorization boundary.

### Audit

Sensitive writes, privileged operations, exports, break-glass events and designated PHI reads are auditable.

### AI

AI cannot bypass RLS, cannot query arbitrary SQL, and cannot independently finalize a clinical decision.

## Re-audit decision

The architecture may become **APPROVED FOR MIGRATION** only after these criteria are backed by concrete implementation specifications and executable tests. Documentation alone is insufficient.

## Migration principles

- Every migration must be idempotency-aware and dependency-ordered.
- No application table should be exposed before its RLS policy is installed.
- SECURITY DEFINER functions must be installed only after their dependent tables exist and before policies that call them.
- Grants must be explicit; avoid accidental PUBLIC EXECUTE.
- No service-role credential is placed in client code.
- Production deployment must use separate dev/staging/prod Supabase projects.
- CI must execute schema validation and security tests before deployment.
